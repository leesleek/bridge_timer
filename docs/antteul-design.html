01한 장 요약

아래 표만 읽어도 무엇을 만들 것인지 판단할 수 있어야 합니다. 나머지 절은 이 표의 근거입니다.

무엇을
교대 구성원 전용 중고거래 + 생활 커뮤니티 앱. 거래는 캠퍼스 내 직거래만, 커뮤니티는 학과·학년을 가로지르는 정보 게시판.
누구에게
재학생(약 1,900명), 대학원생, 교직원·교수(약 400명). 졸업생은 ‘물려주기’ 목적의 6개월 유예 계정만.
왜 필요한가
지금은 에브리타임 장터 글, 학과 단톡, 카톡 오픈채팅에 흩어져 있어 검색이 안 되고, 기록이 남지 않으며, 학기가 끝나면 증발합니다. 당근을 쓰면 학교 밖 사람과 만나야 합니다.
핵심 차별점
① 학교 이메일 인증으로 신원이 확인된 폐쇄망 ② 캠퍼스 안전거래존 기반 직거래 ③ 교대 물품 분류 체계(임용 수험서·실기 도구·교생 정장·교구) ④ 졸업 시즌 물려주기
하지 않을 것
택배·배송 중개, 에스크로 결제, 강의평가, 익명 대나무숲 전면 대체, 타 대학 개방(1단계 한정)
기술 선택
Flutter 앱 + Supabase(서울 리전). 백엔드 서버를 직접 운영하지 않는 구조로, 학생 인력 교체에도 서비스가 죽지 않게 함.
1학기 목표
구성원 가입률 40%, 주간 신규 등록 30건, 주간 성사 거래·나눔 20건, 신고 처리 중앙값 12시간 이내
가장 큰 위험
거래량 부족(콜드스타트). 2,300명 규모에서는 하루 몇 건이 현실적 상한이므로, 거래만으로는 앱을 열 이유가 안 됩니다. → 11절 참조
이 문서의 전제

학교를 경인교대(단일 캠퍼스, 구성원 약 2,300명)로, 개발 주체를 교내 팀(캡스톤·연구실 또는 학생 개발 동아리 2~4인)으로 가정했습니다. 규모가 다르거나 전국 교대 연합으로 간다면 8·10·13절의 결론이 바뀝니다. 16절에 확인이 필요한 항목을 모아 두었습니다.

02문제와 포지셔닝

교대에는 이미 커뮤니티가 있습니다. 그 자리를 뺏으려 하면 집니다. 비어 있는 자리를 정확히 찾아야 합니다.

지금 벌어지는 일

교대생의 중고 거래는 대부분 세 곳에서 일어납니다. 에브리타임 장터 게시판, 학과·학년 단톡방, 그리고 당근입니다. 각각의 한계가 안뜰의 존재 이유입니다.

현재 수단잘 되는 것안 되는 것
에브리타임 장터이미 모든 학생이 씀. 익명이라 부담 없음글이 밀려 내려가면 끝. 사진 관리·검색·찜 없음. 판매자 신뢰도 판단 불가. 거래 후 기록 없음
학과 단톡방즉시 도달. 같은 학번이라 신뢰같은 학과·학년 안에서만. 스크롤 지나가면 소멸. 안 팔리면 재게시 눈치
당근기능 완성도 최고거래 상대가 학교 밖 사람. 캠퍼스 밖에서 만나야 함. 임용 수험서·실기 도구 같은 교대 품목은 검색 노출이 거의 없음
카톡 오픈채팅실시간신원 불명. 사기·노쇼 대응 불가. 졸업하면 방 자체가 사라짐

교대라서 다른 점

이 설계에서 가장 중요한 부분입니다. 종합대 중고장터를 그대로 옮기면 실패합니다. 교대는 다음 네 가지가 구조적으로 다릅니다.

  • 물품이 4년 주기로 돌 수밖에 없습니다. 전공서적, 임용 수험서, 실기 도구(디지털피아노·리코더·단소·오카리나), 미술 재료, 교생실습 정장은 특정 학년에 반드시 필요하고 그 학년이 지나면 반드시 필요 없어집니다. 공급자와 수요자가 학번으로 정확히 갈립니다.
  • 구성원이 적고 서로 압니다. 한 학년 500명 이하, 학과당 40~60명 규모라 익명성이 사실상 없습니다. 사기 위험은 극히 낮지만, 평판 위험은 대단히 높습니다. 신뢰 설계의 방향이 당근과 정반대여야 합니다(5절).
  • 연간 리듬이 뚜렷합니다. 3월 개강(교재 수요 폭증), 6월 종강(교재 처분), 9월 교생실습(정장·교구), 11월 임용(수험서 폐기·나눔), 12월~2월 졸업(자취방·기숙사 대량 정리). 거래량이 균등하지 않고 연 4회 스파이크로 몰립니다.
  • 선후배 물려주기 문화가 이미 있습니다. 다만 아는 후배가 있어야 가능합니다. 이 비공식 관행을 제품화하는 것이 안뜰의 가장 강한 훅입니다.

학교 계정이 필요한 것, 캠퍼스 안에서 끝나는 것, 기록이 남아야 하는 것만 가져옵니다.

한 문장 포지셔닝

“교대 안에서만 통하는 물건을, 교대 사람인 게 확인된 사람에게, 걸어가서 받는 곳.” 이 문장에 해당하지 않는 기능 요청은 전부 후순위로 미룹니다.

03사용자와 시나리오

페르소나 넷과, 각 페르소나가 앱을 처음 연 3분 안에 하는 일입니다. 이 3분이 안 되면 나머지 기능은 의미가 없습니다.

1학년 · 3월

교재를 싸게 구하고 싶은 신입생

수강신청 직후 교재 목록을 받았는데 새 책으로 사면 20만 원이 넘습니다. 선배가 누군지 모릅니다.

첫 3분 가입 → 수강 과목 코드 3개 입력 → 해당 교재 판매글 자동 매칭 목록 → 찜 2개, 채팅 1개.

3학년 · 9월

교생실습을 앞둔 학생

4주만 입을 정장과 구두, 명찰, 실습 교구가 필요합니다. 사기는 아깝습니다.

첫 3분 ‘교생실습’ 카테고리 → 사이즈 필터 → 대여·나눔 글 확인 → 실습 정보 게시판에서 배정 학교 후기 검색.

4학년 · 11월

임용을 준비하는 수험생

수험서가 매년 개정돼 작년 판본은 값이 급락합니다. 시험 끝나면 전부 짐입니다.

첫 3분 판본 연도 태그로 검색 → 스터디 모집 글 확인 → 시험 후 ‘일괄 나눔’으로 12권 한 번에 등록.

교직원 · 상시

연구실·행정실 물품 담당

연구실 정리에서 나온 사무기기, 도서, 교구를 버리기는 아깝고 처리 절차는 번거롭습니다.

첫 3분 교직원 배지가 붙은 계정으로 나눔 등록 → 선착순 대신 ‘사유 적기’ 방식으로 수령자 선택.

핵심 여정: 판매

등록에 3분 이상 걸리면 사람들은 그냥 단톡방에 사진을 던집니다. 등록 화면은 이 기준으로만 평가합니다.

  1. 카메라로 사진 촬영(최대 10장). 첫 장이 대표 이미지, 드래그로 순서 변경.
  2. 카테고리 선택 → 카테고리에 따라 다음 입력 항목이 달라집니다. 교재를 고르면 과목·판본 연도·필기 여부, 의류를 고르면 사이즈, 실기 도구를 고르면 상태 등급이 뜹니다.
  3. 가격 입력 또는 ‘무료나눔’·‘가격 제안 받기’ 토글.
  4. 희망 거래 장소를 안전거래존 목록에서 선택(기본값: 직전 거래 장소).
  5. 등록 → 해당 카테고리를 찜해 둔 사용자에게 푸시.

핵심 여정: 구매와 만남

거래 사고의 대부분은 ‘약속’ 단계에서 생깁니다. 노쇼, 시간 착오, 장소 착오입니다. 채팅에 자유 대화만 두지 않고 약속 카드를 구조화된 객체로 넣습니다.

  • 채팅방 상단에 항상 물품 카드가 고정됩니다(가격·상태·판매중/예약중).
  • 판매자가 ‘약속 잡기’를 누르면 장소·날짜·시간 선택 카드가 채팅에 삽입되고, 구매자가 수락하면 양쪽 캘린더 알림이 잡힙니다. 30분 전 푸시.
  • 약속이 확정되면 물품 상태가 자동으로 ‘예약중’으로 바뀌고 다른 사람의 채팅 요청은 대기열로 갑니다.
  • 약속 시각 2시간 뒤 양쪽에 “거래가 잘 끝났나요?” 알림. 양쪽이 확인해야 ‘거래완료’가 되고, 이때만 평가가 열립니다(5절).
  • 노쇼 신고는 이 시점에만 가능하며, 상대에게는 내용이 공개되지 않고 운영진에게만 누적됩니다.

우선순위는 M MVP 필수 · S 정식 출시 · C 검토 대상. M에 없는 것은 MVP에서 만들지 않습니다.

교대 특화

안뜰만의 것
  • M교대 카테고리 체계(아래 표) 및 학번 기반 ‘내 학년 추천’
  • S물려주기 — 졸업 예정자가 여러 물건을 한 묶음으로 내놓고, 후배가 ‘받고 싶은 이유’를 적어 신청하는 비가격 매칭
  • S임용·실기 스터디 매칭(과목·선발지역·시간대 조건)
  • S교생실습 정보(배정 학교별 후기, 복장 규정, 필요 물품 체크리스트)
  • C기숙사 층별 나눔 선반(오프라인 연계, 무인 수령)
  • C졸업생 유예 계정에서의 후배 멘토링

당근의 매너온도를 그대로 가져오면 안 됩니다. 서로 아는 2,300명 커뮤니티에서 공개 평판 점수는 다르게 작동합니다.

매너온도를 쓰지 않는 이유

당근의 36.5도 시스템은 익명의 대규모 모집단에서 작동합니다. 점수가 낮아도 다른 동네로 가면 그만이고, 상대를 다시 만날 일이 없습니다. 교대는 반대입니다. 낮은 점수를 받은 학생은 4년 동안 같은 건물에서 그 사람을 마주칩니다. 결과는 두 가지로 나타납니다. 아무도 부정적 평가를 하지 않아 점수가 의미를 잃거나, 한 번의 분쟁이 보복 평가로 번져 학내 갈등이 됩니다. 어느 쪽이든 실패입니다.

  where status in ('on_sale','reserved');
create index items_cat_idx  on items (category_id, bumped_at desc)
  where status = 'on_sale';
-- jsonb 속성 검색(과목코드 등)
create index items_attrs_idx on items using gin (attrs jsonb_path_ops);
한국어 검색은 여기서 갈립니다

PostgreSQL의 기본 전문 검색에는 한국어 형태소 분석기가 없습니다. to_tsvector('simple', ...)로는 “초등수학교육”을 검색해도 “초등 수학 교육의 이해”가 걸리지 않습니다. 데이터 규모가 작으므로(연 수천 건) pg_bigm 확장 + GIN 인덱스로 2-gram 부분 일치를 쓰는 것이 가장 비용이 낮고 정확합니다. 확장 설치가 불가한 환경이면 pg_trgm이 차선이지만 한글에서는 정확도가 떨어집니다. 어느 쪽도 안 되면 제목·본문·과목코드를 이어 붙인 search_text 컬럼에 ILIKE '%키워드%'를 쓰고, 수만 건을 넘어서면 그때 전용 검색 엔진을 검토합니다. 처음부터 Elasticsearch를 얹는 것은 이 규모에서 명백한 과잉입니다.

행 수준 보안(RLS) 예시

백엔드 서버 없이 클라이언트가 DB에 직접 접근하는 구조를 택했으므로, 권한은 전부 DB 정책으로 강제됩니다. 이 정책이 곧 보안 경계입니다.

alter table items enable row level security;

-- 읽기: 인증 완료된 구성원만. 숨김 처리된 글은 작성자와 관리자만
create policy items_read on items for select
  using (
    exists (select 1 from profiles p
            where p.id = auth.uid()
              and p.verified_at is not null
              and p.status = 'active')
    and (status <> 'hidden' or seller_id = auth.uid() or is_admin())
  );

-- 쓰기: 본인 글만. 제재 중인 계정은 등록 불가
create policy items_write on items for insert
  with check (seller_id = auth.uid() and not is_restricted(auth.uid()));

-- 평가는 평가자만 읽을 수 있음. 피평가자는 자기 평가를 볼 수 없음
create policy reviews_read on deal_reviews for select
  using (rater_id = auth.uid() or is_admin());

메시지 테이블에는 room_id를 통한 참여자 확인 정책을 걸고, 관리자 조회는 별도 서버 함수를 거쳐 audit_logs에 기록이 남게 합니다. 관리자 키(service role)는 클라이언트 앱에 절대 포함하지 않으며, 관리자 콘솔은 별도 웹으로 분리합니다.

09구성원 인증

안뜰의 모든 신뢰가 이 단계 하나에 걸려 있습니다. 여기가 뚫리면 그냥 작은 당근이 됩니다.

방식구현신뢰도학교 협조판단
A. 학교 이메일 OTP@ginue.ac.kr 주소로 6자리 코드 발송중상 — 계정 보유 = 구성원불필요MVP 채택
B. 학교 SSO / LDAP 연동학사시스템 계정으로 로그인, 소속·학년 자동 취득높음필수(정보전산팀 심의)정식 출시 목표
C. 학생증·재학증명서 심사사진 제출 후 운영진 수동 확인높음불필요비권장 — 민감정보를 직접 보관하게 됨

A로 시작해 B를 목표로 합니다. C는 신분증 이미지라는 가장 민감한 데이터를 떠안게 되므로, 예외 승인(교환학생·계약직 등)에서만 확인 후 즉시 파기 조건으로 씁니다.

A안의 구멍과 막는 법

  • 졸업생 계정 잔존 — 많은 대학이 졸업 후에도 메일 계정을 유지시킵니다. 매 학기 초 재인증을 요구하고, 재인증에 실패하면 ‘졸업생’ 상태로 자동 전환해 구매·나눔 수령만 가능하고 판매·커뮤니티 작성은 막습니다. 유예 6개월.
  • 계정 대여 — 한 사람이 여러 기기에서 로그인해 대리 거래를 하는 경우. 기기 지문을 세션에 묶어 동시 활성 기기를 2대로 제한하고, 새 기기 로그인 시 재인증합니다.
  • 이메일 별칭·전달 — 점 표기나 플러스 별칭으로 한 계정에서 여러 가입. 이메일을 정규화(소문자·점 제거·플러스 이후 절단)한 뒤 해시해 유일 제약을 겁니다.
  • 무차별 코드 시도 — 코드 6자리, 유효 10분, 5회 실패 시 30분 잠금, 동일 IP 시간당 발송 10회 제한.
  • 소속·학년의 정확성 — A안에서는 학과·입학년도를 본인이 입력하므로 틀릴 수 있습니다. 프로필에 “본인 입력” 표시를 하고, B안 연동 후 “학교 확인됨” 배지로 승격합니다.
수집하지 말아야 할 것

이름, 학번, 생년월일, 연락처는 저장하지 않습니다. 안뜰이 필요로 하는 것은 ‘이 사람이 우리 학교 구성원인가’ 하나뿐이고, 그것은 이메일 해시로 충분합니다. 개인정보를 적게 가질수록 사고 시 피해와 법적 의무가 함께 줄어듭니다. 학번을 화면에 표시할 때도 수학교육 22처럼 학과와 입학년도만 씁니다.

구성원 2,300명 규모에서 중고 거래만으로는 하루 5~15건이 현실적인 상한입니다. 그 정도로는 앱을 매일 열 이유가 없고, 앱을 안 열면 매물도 안 올라와 거래량이 더 줄어드는 악순환이 생깁니다. 대부분의 교내 장터 앱이 여기서 죽습니다. 따라서 안뜰은 거래 앱에 커뮤니티를 곁들이는 것이 아니라, 매일 열 이유(커뮤니티·분실물)를 먼저 만들고 거래를 그 위에 얹는 순서로 가야 합니다.

순서

  1. 분실물부터 엽니다. 만들기 쉽고, 수요가 확실하며, 학교 규모와 무관하게 매주 발생합니다. 행정실·도서관·학생회관 습득물을 운영진이 대신 올려 주면 첫 주부터 콘텐츠가 있습니다. “안뜰 = 잃어버린 거 찾는 앱”으로 먼저 각인시킵니다.
  2. 커뮤니티 두 개만 활성화합니다. 수업·과제 질문, 스터디 모집. 운영진이 주 2회 마중물 글을 올리고, 답이 없는 질문에는 24시간 안에 반드시 답을 답니다.
  3. 거래는 시즌에 맞춰 붙입니다. 아래 캘린더의 진한 달에 맞춰 정식 오픈합니다. 3월 개강 첫 주 또는 12월 졸업 시즌 중 하나를 D-day로 잡습니다.
  4. 물려주기로 공급을 한 번에 만듭니다. 졸업 예정자에게 “버릴 것 말고 물려줄 것” 캠페인. 졸업생 한 명이 평균 10~20개를 내놓으면 100명만 참여해도 매물 1,500건이 생깁니다. 수요가 아니라 공급을 먼저 채우는 것이 마켓플레이스 콜드스타트의 정석입니다.

16확인이 필요한 것

아래 다섯 개의 답에 따라 이 문서의 일부를 다시 씁니다. 순서대로 중요합니다.

  1. 운영 주체를 학교로 할 것인가, 학생 단체로 할 것인가. 10절 전체와 13절의 계정 소유권, 9절의 SSO 가능 여부가 여기에 달려 있습니다.
  2. 개발 주체와 기간. 캡스톤 수업(한 학기)인지, 연구실 과제(1~2년)인지, 외주인지에 따라 12절 로드맵의 현실성이 달라집니다. 한 학기짜리라면 MVP 범위를 더 잘라야 합니다.
  3. 대상 범위. 한 학교 전용인지, 전국 10개 교대 연합인지. 연합이면 규모 문제(11절)는 풀리지만 ‘캠퍼스 안 직거래’라는 핵심 전제가 무너져 완전히 다른 제품이 됩니다.
  4. 앱 우선인가 웹 우선인가. 이 문서는 앱 우선으로 썼습니다. 인력이 2인 이하라면 반응형 웹으로 시작하고 푸시를 포기하는 선택도 가능합니다.
  5. 익명 게시판을 열 것인가. 4절 말미의 판단을 학교·학생회와 사전에 합의해 두는 편이 안전합니다.
